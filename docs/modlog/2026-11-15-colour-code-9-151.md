## In-line colour code 9: what draws it and what uses it (2026-11-15)

<!-- dll-build: 30261102_0 -->

Queue row 151, from the 30261102_0 re-baseline: that build gave in-line colour code 9 (`1e 09`) a colour, and the row
asked which retail text uses it and whether the client draws it. It was an audit. The client already drew it and
nothing changed in the drawing; two tests now hold it. All addresses are build 30261102_0.

**The table.** 0x10336510 holds 17 D3DCOLOR values, one per code `1e 00` .. `1e 10`:

| code | value | | code | value |
|---|---|---|---|---|
| 0, 1 | 0 (the line's colour) | | 6 | 0x60108080 |
| 2 | 0x4040c000 | | 7 | 0x60c09060 |
| 3, 4 | 0x604040a0 | | 8 | 0x80804020 |
| 5 | 0xffa02080 | | 9 | 0x60404040 (was 0 through 30261006_0) |
| | | | 0xa .. 0x10 | 0 |

Code 9 is blue, green and red all 0x40, half of the font's full 0x80: a half-bright grey.

**The one reader.** FUN_101635a0 (code) is the only function that touches the table (one data reference, at
0x101635af; nothing addresses the entry at +0x24 on its own). It takes the code's absolute value, returns the
table entry below 0x11 and FUN_1012b190 (the colour-id table, 0x80808080 when the id is absent) from 0x11. Its only
caller is the log line drawer FUN_10163710 (glyph words, count, line colour, x, y, alpha, cursor flag, window):

- the alpha argument replaces the alpha of every colour the draw uses, 0x80 when it is 0 (FUN_101635c0), so the
  table's own alpha byte (0x60 for code 9) is never drawn;
- a word in -0x1ff ..= -0x100 is `1e xx`: the running colour becomes FUN_101635a0's value, or the line's colour
  when that value is 0;
- a word below -0x1ff is `1f xx`: chat mode xx's colour (FUN_1012b100);
- a word in -0xff ..= -1 (a `7f xx` code) draws nothing and changes nothing.

The words come from FUN_1011e640 (the same conversion is at 0x10129980), which turns the bytes `1e xx` into
-0x100 - xx. FUN_1012b980, the log's line wrapper, starts each wrapped line with the last `1e xx` seen (`1e 01`
at first), so a code 9 run carries over a line break like any other code.

**Ours.** `Font::layout_line` is FUN_10163710's colour rule, `Font::code_colour` the same rule for the runs the
modern UI draws, and the modern chat's `line_job` reads the same 17 entries; all three take the table from the
FFXiMain.dll in use (`dat::tables::code_colours`, signed over codes 0..8 since the re-baseline), keep the draw's
alpha and fall back to the line's colour on 0. `GameUi::wrap_indent` carries the last code over a wrap. So with a
30261102_0 DLL code 9 draws 0x404040 at the line's alpha, and with 30261006_0 it leaves the line's colour, as retail
did in each build.

**What uses it: nothing the client holds.**
- The DLL writes a `1e` code itself in four functions only, through FUN_100be680 (buffer, code): 0x100be060,
  0x100be760, 0x100bf3e0 and 0x100c0500, the message formatters. The codes they pass are 2, 3 and 8 (and
  FUN_100be690 writes `1e 01`, the way back). FUN_100c2bf0 copies a code it is given. None writes 9, and the DLL's
  data has no string with `1e 09` in it.
- The dialog files (1,288 files, text XOR 0x80), counting every `1e xx` pair in their text: codes 1 (6,367), 5
  (6,259), 4 (78), 2 (30) and 7 (30). None uses 9.
- The d_msg files (259) hold no `1e` code from 0 to 0x10.
- A scan of all 53,024 DAT files of the 30261102_0 install for `1e 09` before text, plain and under each text
  coding the client has (XOR 0xff, XOR 0x80, the seven bit rotations), finds only texture and vertex data.

So in this build nothing the client holds puts code 9 on screen. The log draws it for any line whose bytes hold
`1e 09`. s2c 0x017 chat cannot bring one (FUN_10191210 cuts a chat line at its first 0x1e), which leaves other
text the server sends. Whether a retail message carries it, and which, needs a retail capture; the client side is
complete without it.

**Tests.** `dat::tables::tests::found_in_the_installed_build` takes 0 or 0x60404040 for code 9 and 0 for codes
0xa..0x10. `dat::font::tests::colour_code_9` lays out `a 1e09 bc 1e01 d` with the installed font and checks the
glyph colours (the table's colour at the line's alpha, then the line's colour again) and that the codes take no
room.
